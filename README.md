# 🦅 Rime Hawk — 鹰眼辅码精准过滤插件

> **一句话简介：** Hawk 是一个工作在 Rime 候选列表后处理阶段的 Lua 候选过滤器 (filter)，通过「拼音+辅码」模式实时筛选同音字，以鹰眼般的精准度实现键键有反馈的即时定位，同时提供强大的长句断句与底层修音功能。

## 一、核心理念

> **拼音 + 辅码 = 鹰眼锁定**  
> 拼音输入法同音字太多，选择目标词的成本过高。Hawk 绝不改变底层引擎的拼音解析行为（预编辑 preedit），而是在拼音（音维度）给出候选列表后，利用追加的辅码（形维度）进行实时精准的筛选与截断——如同猎鹰从高空锁定猎物，一击命中。

## 二、辅码表说明

插件依赖外部的纯文本字典文件（UTF-8 编码），每行以制表符 (`<TAB>`) 分隔字与辅码。

*   辅码通常为两位英文字母。
*   一个字可支持多个辅码（使用逗号 `,` 分隔）。
*   同一字的多个辅码也可分多行书写，引擎在加载时会自动合并。

**示例辅码数据（基于验证数据 `test5.txt`，虎码首末大码）：**

| 字 | 辅码 | 字 | 辅码 |
|---|---|---|---|
| 心 | hh | 最 | or |
| 仪 | jb | 嘴 | dt |
| 观 | re | 啊 | dz |
| 一 | fi | 阿 | tz |
| 踩 | pe | 爱 | yr |
| 祎 | fg | | |

## 三、快速部署

仅需 4 步即可完成部署配置：

1.  **放文件**：将 `aux_v2.lua`（或调试版 `aux_v2_debug.lua`）脚本及辅码表文件（如 `test5.txt`）置于 `<Rime用户目录>/lua/` 目录下。
2.  **改 YAML**：在你的输入方案配置文件（如 `.schema.yaml`）中完成以下配置：

```yaml
speller:
  # 必须确保包含引导键(;)、切换键(`)和占位符(,)等所有插件使用的符号
  alphabet: zyxwvutsrqponmlkjihgfedcba;`,

engine:
  filters:
    - lua_filter@aux_v2@test5@on@;@`@,@s
```

3.  **Hook preedit_format（双拼方案必做）**：如果你的方案 YAML 中存在 `translator/preedit_format` 字段，**必须将其更名为 `preedit_format1`**。Hawk 需要接管此参数进行拼音串的反演转换，若不改名将导致断句、修音等功能全面失效。

```yaml
translator:
  # ❌ 原始写法（会与 Hawk 冲突）
  # preedit_format:
  #   - xform/.../.../

  # ✅ 改名为 preedit_format1，交由 Hawk 接管
  preedit_format1:
    - xform/.../.../
```

4.  **重新部署**：在 Rime 菜单中点击重新部署即可生效。

## 四、配置参数详解

方案 YAML 中的挂载参数由 `@` 符号分隔，**以下 6 项顺序固定且每项必填**：

| # | 参数 | 说明 | 示例配置 |
|---|---|---|---|
| 1 | `path` | 辅码表文件名（**不带** `.txt`） | `test5` |
| 2 | `showor` | 是否在候选项旁显示辅码提示 | `on` / `off` |
| 3 | `trigger` | 引导键 | `;` |
| 4 | `switch` | 单字/词组模式切换键 | `` ` `` |
| 5 | `ph` | 占位符（用于触发主动分心或填补指令位） | `,` |
| 6 | `matchmode` | 匹配模式（决定辅码匹配的顺序严格度） | `s` |

> [!NOTE]
> **💡 源码探究：matchmode 参数的 `s` 与 非 `s` 究竟决定了什么？**
> 
> 查阅 `AuxFilter.match` 源码可知，该参数决定了对辅码匹配的**顺序和宽容度限制**：
> *   **`s`（严格顺序模式）**：输入单码时，**仅匹配辅码的第一位**；输入双码时，必须严格遵守"首码+末码"的先后顺序。
> *   **非 `s`（如 `m`，宽松乱序模式）**：输入单码时，匹配首位或末位均可命中；输入双码时，**允许颠倒顺序**（即字典辅码为 `ab`，用户乱序输入 `ba` 也视为正确）。

## 五、功能一：辅码筛选

这是最核心的功能。输入拼音后，按下引导键 <kbd>;</kbd> 并紧跟辅码进行过滤。

*   **单码筛选**：输入一位辅码进行特征粗筛，不符合该辅码特征的字将被无情隐藏。
*   **双码精确筛选**：输入两位辅码进行精确定位（结合双拼，通常 4 键可精确定位单字）。
*   **辅码提示**：当 `showor=on` 开启时，候选词旁将直接带上括号提示辅码。

**操作示例（想打"踩 pe"）：**

**步骤 1：全拼输入完毕，尚未输入辅码时，默认展示所有同音字及其辅码提示**
```text
cai
① 踩(pe)  ② 菜(le)  ③ 才(nt)
```

**步骤 2：按下引导键 ; 并输入首码 p。引擎瞬间发力，由于"菜(le)"和"才(nt)"的辅码首位不是 p，它们被当场剔除消失！**
```text
cai ;p
① 踩(pe)
```

**步骤 3：如果同首码下还有其他字，可继续输入次码 e，精确定位到唯一匹配的双码候选**
```text
cai ;pe
① 踩(pe)
```

## 六、功能二：偏移指令

在辅码位输入完毕后，如果需要微调选段的长度或跳过特定候选，可追加偏移指令。

> [!WARNING]
> **💡 源码勘误：偏移机制的真实逻辑限制**
> 
> 知识库原文档称 d/f 可使候选长度增加。经查阅源码，截取补偿值被严格限制为 `math.min(0, S.rightcompen - S.leftcompen)`。这意味着**右偏指令 (d/f) 无法强制突破引擎原有的拼音匹配上限长度，它们的作用仅仅是用来"抵消"（撤销）误触 a/s 时造成的左偏截取效果**。

| 按键 | 方向 | 实际效果说明 |
|---|---|---|
| <kbd>a</kbd> | 左偏 | 候选截取长度 -1 |
| <kbd>s</kbd> | 左偏 | 候选截取长度 -2 |
| <kbd>d</kbd> | 右偏 | 抵消 1 次左偏恢复长度 |
| <kbd>f</kbd> | 右偏 | 抵消 2 次左偏恢复长度 |
| <kbd>w</kbd> | 跳过 | 跳过当前第 1 个候选，让第 2 个候选升为首位 |

## 七、功能三：分心机制

独创的「跨字分配辅码」。当你打二字词时，输入的两位辅码如果不匹配任何完整的单字辅码，引擎会将双码拆解，分别作用于词组的第一字和第二字。

### 1. 被动分心 `**`（双码恰好命中首尾）

想打「心仪」（心=hh, 仪=jb），二字词组被自动拆分命中。

**步骤 1：输入 xinyi (心仪候选位在第 5 位)**
```text
xin yi
① 心怡  ② 新一  ③ 心意  ④ 新意  ⑤ 心仪
```

**步骤 2：输入单码 ;h 筛选心字头词汇**
```text
xin yi ;h
① 心意  ② 心仪  ③ 欣怡  ④ 馨怡  ⑤ 心疑
```

**步骤 3：组合输入次码 j，触发被动分心匹配首字和次字**
```text
xin yi ;hj
① 心仪 **
```

### 2. 被动分心 `*x`（首字命中，次字延续）

> [!IMPORTANT]
> **💡 源码勘误：前瞻探路 (Look-ahead Validation) 保护**
> 
> 发生 `*x` 截断前引擎会向后探测下一个拼音音节（如 yi）。**只有当下一个音节真正包含符合次码规则的字（探路成功）时，才会放行并打上 `*x` 截断标识**；否则引擎将判定为死胡同并拦截操作，拒绝产生虚假诱导。

如果你记错了「心仪」的拼音，错误输入了辅码 `hf`：

**步骤 1：输入 xinyi;hf**
```text
xin yi ;hf
① 心 *x
```
*👉 机制解析：h 匹配了「心」，而 f 无法匹配仪/意/怡等字。引擎向后探路发现后续音节 yi 内存在带 f 辅码的字（一/fi），探路成功，于是将词截断保留单字「心」，带出 \*x。*

**步骤 2：空格确认「心」上屏，遗留的辅码 f 自动作用于下一轮筛选**
```text
yi ;f
① 一(fi)  ② 口  ③ 祎(fg)
```

### 3. 主动分心 `✂` 与 `⇐`

如果在辅码后追加配置的占位符 `,`，即可跳过验证，强制触发跨字分配。

> [!NOTE]
> **💡 源码勘误：主动分心的标记定义**
> 
> 根据源码逻辑，使用占位符主动分心时：如果双码完美命中目标词首末，保留整词并标注 `⇐`；如果无法完美命中造成强制被动截断，留下来的单字才会标注 `✂`。

```text
xin yi ;hj,
① 心仪 ⇐
```

**分心标记对比速查：**

| 标记 | 含义 | 候选展示效果 | 辅码去向 |
|---|---|---|---|
| `**` | 被动触发，双码分别命中首尾两字 | 完整二字词 | 消耗完毕 |
| `*x` | 被动触发，仅首码命中且次码探路成功 | 截断为首位单字 | 次码保留给下一轮作为筛选 |
| `⇐` | 主动追加 `,`，双码完美命中 | 完整二字词 | 消耗完毕 |
| `✂` | 主动追加 `,`，未完美命中迫使截断 | 截断为首位单字 | 次码保留给下一轮作为筛选 |

## 八、功能四：单字筛选模式

不需要修改配置选项，在引导键 `;` 后紧接切换键 `` ` ``，即可打散所有候选词，强制进入一整轮的逐字挑选状态。

> [!TIP]
> **💡 机制揭秘：即用即消的单字切换键**
> 
> **单字切换符 `` ` `` 是一个状态切换开关。**
> 
> 当您键入它时，引擎会立即将内部状态变更为"单字模式"，同时**将该符号从输入串中瞬间抹除（自毁隐形）**。这意味着之后的输入框看起来只有 `;`。
> 
> 接下来的流程就是**一轮彻头彻尾的单字模式**。这和普通辅码筛选完全一样，只不过被强制锁死在了纯单字上。在这个模式下，您继续敲击字母（例如 `w`），它就是作为**第一位辅码**，去粗暴直接地过滤那些不符合特征的单字！

**操作实例：逐字精准输出「单字模式」四个字**

**步骤 1：全拼输入，默认优先展示整词**
```text
dan zi mo shi
① 单子模式  ② 单字  ③ 单子  ④ 胆子
```

**步骤 2：键入 ; 后按下 ` 键触发单字模式。此时 ` 被瞬间消掉，引擎带出分支提示，且列表打散刷新为纯单字**
```text
dan zi mo shi ; 【单字筛选分支】
① 单(hn)  ② 但(jf)  ③ 旦(of)  ④ 淡(kc)
```

**步骤 3：空格确认「单」上屏后，列表滑入下一音节（zi）。直接键入辅码 w，瞬间过滤掉所有不相干的非 w 字，精确留下匹配成功的目标字！**
```text
zi mo shi ;w 【单字筛选分支】
① 字(wh)
```
*👉 完美证明：此时的 `w` 是在执行辅码筛选！原本列表里的 `自(oi)`、`紫(hn)`、`姊(hy)` 等字因为辅码不含 w，被直接干净利落地过滤掉了。后续以此类推，当所有音节逐一确认上屏后，这一轮单字模式自动结束，引擎切回正常的词组模式。*

## 九、功能五：长句断句

针对超长拼音串引擎自动组词错误时，可通过辅码特征定位并**精确截取断点**。  
**关键特性**：断句确认后辅码不会被清除消失，它会持续对后续剩余的候选生效！

**操作实例：想打「我的无力成了我的败笔」（无=dd）**

**步骤 1：引擎错把 wu li 认成"物理"。输入单码 ;d 标记出潜在断点**
```text
wo de wu li cheng le wo de bai bi ;d
① 我的<...
```

**步骤 2：补足辅码 ;dd，精准锁定两处断点（由于命中 wu 和 li 两字）**
```text
wo de wu li cheng le wo de bai bi ;dd
① 我的<无力成了我的败笔
```

**步骤 3：追加 ; 执行断点截取指令（默认从断点处截断其前面的部分）**
```text
wo de wu li cheng le wo de bai bi ;dd;
① 我的
```

**步骤 4：确认上屏后，未消耗的 dd 自动继续向后穿透发力，精准命中"无"字！**
```text
wu li cheng le wo de bai bi ;dd
① 无力成了我的败笔
```

## 十、功能六：修音（极客纠错）

长句断句的终极延伸！当我们在打长句时手滑敲错了一个音节，通常只能狂按 Backspace 删掉一大半重打。而在 Hawk 中，可以在错误位置断句后执行 `s` 指令，**直接将由于手滑输入错的音节编码原地篡改重写！免删重打！**

**操作实例：想打「最佳歌手」，但在双拼连打时不小心把 `ge` 按成了 `gr`（`gr` 对应 `guan/观`，观的辅码=re）。**

**步骤 1：输入完整的双拼串，发现中间敲错了一个键（ge 错敲成了 gr，被引擎正确无误地解析为 guan/观）**
```text
zv jx gr uz
① 最佳观收  ② 最佳  ③ 醉驾  ④ 最(or)
```

**步骤 2：用当时错打出来的字（观）对应的辅码 ;r 顺藤摸瓜，定位错误音节的断点位置**
```text
zv jx gr uz ;r
① 最<佳<观收
```

**步骤 3：补齐 ;re 精确圈定在「观」处**
```text
zv jx gr uz ;re
① 最佳<观收
```

**步骤 4：追加 ; 执行断点切分截取**
```text
zv jx gr uz ;re;
① 最佳
```

**步骤 5：输入修音指令 sge（原地将截取位置后方的那个因为手误打错的音节 gr，强制重写为您真正想打的 ge）**
```text
zv jx gr uz ;re;sge
① gr->ge
```

**步骤 6：按空格敲击确认，底层预编辑串被重构，引擎重新按正确发音拼读，完美纠错！**
```text
zv jx ge uz
① 最佳歌手  ② 最佳  ③ 醉驾  ④ 最(or)
```

## 十一、功能七：动态性

Hawk 拥有极致的**键键有反馈**设计哲学。系统对第一候选存在特殊的动态意图捕捉：当你输入第一位辅码展出了第一候选时，若你不执行确认操作而是继续输入第二个辅码，这就等于向引擎明确声明"我对目前的首选不满意"，引擎会直接动态抛弃它并重排剩余的候选列。熟练掌握该机制可实现无候选框盲打。

## 十二、功能八：智能指令

在辅码位满后（或利用占位符填满），可通过特定的字母序列调用高阶数据处理指令：

| 类型 | 键入序列 | 实际控制效果 |
|---|---|---|
| **复制截取** | <kbd>c</kbd> | 触发复制模式，并将当前首选内容复制 1 次 |
| | <kbd>cc</kbd> / <kbd>cv</kbd> / <kbd>cb</kbd> / <kbd>cn</kbd> | 复制次数 +1 / ×2 / ^2 / -1 |
| **转译交互** | <kbd>t</kbd> | 进行简繁转换（依赖自带的 OpenCC s2t） |
| | <kbd>tXX</kbd> | 将首选词汇发至外部 API 翻译为 XX 语种（需本地 HTTP 8080 端口支撑） |
| | <kbd>rXX</kbd> | 发送原始拼音输入串请求翻译（需本地 HTTP 8080 端口支撑） |

## 十三、输入模式总览

由于底层利用了精妙的正则表达式对指令进行分流，Hawk 的各个功能形成了无缝的联动：

| 输入形式 | 触发系统功能 | 核心联动机制 |
|---|---|---|
| `pinyin` | **直通** | 完全遵循原汁原味的 Rime 引擎过滤 |
| `pinyin;a` | **单码粗筛** | 输入第一位辅码，按特征粗略筛选候选 |
| `pinyin;ab` | **双码精确筛选** | 输入两位辅码，精准定位目标字；如无匹配候选，对二字词触发被动分心 |
| `pinyin;ab,` | **主动分心** | 双码后追加占位符 `,`，对二字词强制跨字分配辅码 |
| `pinyin;` + `` ` `` | **单字模式** | 即用即消，接下来进行一整轮的单字辅码筛选 |
| `pinyin;ab;` | **长句断句** | 断句 + 偏移 = 灵活微调截取节点 |
| `pinyin;ab;sfoo` | **修音纠错** | 断句 + 修音 = 免删重打！原位修正手滑打错的拼音音节 |

## 十四、运行环境与依赖

Hawk 为纯 Rime Lua 环境扩展，所有核心功能仅依赖 Rime 内建 API（`rime_api`、`Memory`、`Projection`、`Opencc`），无需额外安装。

| 外部依赖 | 属性 | 说明 |
|---|---|---|
| `simplehttp` | 可选 | 驱动 `tXX` / `rXX` 翻译指令的 HTTP 请求。未安装时自动降级，翻译功能静默返回空值，不影响其他功能。 |

## 十五、日志与调试

针对排障与性能监控，`aux_v2_debug` 版本提供了详尽的诊断体系：

*   **结构化调试日志（Debug Log）**：修改源码首部的 `DEBUG_MODE = true` 以开启。以 JSON Lines 格式流式写入至 `<Rime用户目录>/debug_breakpoint.log`，全量记录前瞻探路逻辑与堆栈流转追踪，可结合自带的 `docs/log_parser.html` 工具进行图形化解析诊断。
*   **普通运行日志（Dic Log）**：直接输出至 `<Rime用户目录>/dic.log`，负责记录辅码表的装填状态、`Memory` 接口初始化以及系统基底加载事件。

## 十七、注意事项与已知限制

1.  **`preedit_format` 冲突（致命冲突项）**  
    详见部署步骤第 3 条。此项为双拼方案的必做操作，全拼方案通常无此字段可忽略。
2.  **极短简拼断点搜寻局限**  
    受限于原生底层 Memory API 能力，使用单字母等极短的简拼特征进行查询时，可能会因命中面过宽导致引擎返回空集。这意味着在长句首字母简拼中强行切分断句可能会遭遇寻点失败。
3.  **v2 版本架构红利宣告**  
    在之前的旧版本中，修音分支常常因为原地修改已被缓存的 `inputspls` 数组而直接引发污染闪退。在当前版本中，我们重构使用了 `fresh_spls` 数组安全深拷贝策略，完美根除了越界访问引发的引擎崩溃问题，稳定性得到极大提升。
