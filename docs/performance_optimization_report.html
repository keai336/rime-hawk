Rime Lua 辅码脚本性能优化报告

基于 aux_v2.lua 的静态分析，重点评估候选过滤热路径、辅码表数据结构、Memory API 查询、缓存策略和 UTF-8 字符处理。报告偏向可执行的工程改造，不包含运行时 profiling 结果。

日期：2026-05-01 分支：codex-elegant-aux-trigger-fix 脚本：aux_v2.lua / aux_v2_debug.lua 样本辅码表：test5.txt，25,584 行

结论摘要

高 最高收益：普通辅码筛选热路径的匹配结构和候选遍历
中 数据结构收益：辅码字符串改索引表或 bitset
低 微优化：UTF-8 子串、table.insert、重复 gsub/match
先测 建议先加采样计数器，再做结构重写
P0候选列表目前存在重复遍历，属于热路径结构性成本。

main1() 的 process_candidates() 先遍历一次找首个候选并处理，再从头遍历一次处理所有候选。首候选会被重复进入 main_main()，依靠去重状态抵消输出，但计算成本仍然存在。

P2get_syllable_aux_set() 的 iter_dict() 是低频路径的延迟尖刺，不是主吞吐瓶颈。

断句、修音、分心属于低频能力。这里的 dict_lookup() / iter_dict() 成本可能很高，但只在特定功能触发时出现；优化目标应是控制卡顿和重复扫描，不应抢在普通辅码筛选热路径前面。

P0辅码表运行时仍以字符串为主，普通筛选每次匹配都要扫描。

AuxFilter.aux_code[字] = "pe,xx" 对展示友好，但热路径里 AuxFilter.match()、isCharInFirstPosition()、fullAux() 都需要从字符串恢复结构。建议保留展示字符串，同时新增专用索引。

频率权重优化排序应以“每次按键都会走”的路径为主。

普通单码/双码辅码筛选是高频路径，候选迭代、辅码匹配、候选构造都应优先优化。断句、分心、修音虽然单次开销可能更大，但触发频率低，适合作为第二梯队做有界缓存和尖刺治理。

当前执行链路

输入解析Update_codes() 拆 input/preedit，得到辅码尾段和前缀。
候选迭代main1() 遍历候选，进入 main_main()。
辅码匹配单字走预计算，多字走 fullAuxCache。
低频断句探路get_syllable_aux_set() 经 Memory API 查音节可用辅码。
候选产出candisub:new() 裁剪 preedit/text，再 yield()。

主要复杂度来源

位置 当前行为 复杂度/风险 建议方向
main1.process_candidates() 候选迭代两次，首候选进入处理两次。 候选越多，重复匹配、注释拼接、候选构造越多。 改单次遍历：第一次命中时记录 firstcandi/rawpreedit，同时继续处理后续候选。

AuxFilter.match() 扫描 {首码串, 次码串} 判断匹配。 每个候选都可能扫字符串，候选列表长时明显。 用 char-set 表或 bitmask 表达首码、次码、双码组合。
candisub:new() 频繁 split preedit、transform preedit、构造临时候选。 候选越多，短生命周期 table 越多，GC 压力上升。 缓存 preedit 元数据和 prefix byte offsets；只在真正要输出时做转换。
utf8sub() 多处通过 utf8.offset() 取字符。 对长词/长句多次调用时重复扫描。 候选级 char array 缓存，复用首字、末字、第 N 字。

性能与内存变化对比

下表是静态推导对比，不是实测压测数据。这里按使用频率加权：普通辅码筛选是高频路径，断句、分心、修音是低频路径。符号说明：N 是当前轮候选数，K 是单字模式下为了找到第一个可用候选而跳过的候选数，S 是同一轮参与探路的音节数，U 是重复出现的唯一音节数。

CPU / 延迟对比

优化项 当前成本 优化后成本 变化判断
候选单遍历 普通模式约 N + 1 次 main_main()；单字模式可能额外扫描 K 个候选。 稳定为 N 次候选处理；首候选不再重复进入匹配和候选构造。 CPU 下降 候选越多越明显；行为风险中等。

内存对比

优化项 当前内存形态 优化后内存形态 变化判断
辅码索引表 aux_code[字] = "pe,xx"，展示和匹配共用字符串；另有 fullAux_precomputed。 短期并存 aux_display 和 char_aux_index；若用表集合，启动内存会上升；若用 bitmask，可控制为每字少量整数。 内存上升 换取匹配 CPU 下降。建议稳定后替代旧 fullAux_precomputed，避免双份结构长期并存。

关键取舍最值得做的是“用一点固定内存换热路径稳定”。

辅码索引表是主线，因为普通筛选每次按键都会用；LRU 是低频能力的尖刺治理，容量要小。对输入法脚本来说，高频路径应该用固定内存换稳定低延迟；低频路径只做有界缓存，避免为偶发功能付出过高常驻内存。

数据结构建议

1. 分离展示数据和匹配索引

当前 AuxFilter.aux_code 同时承担展示和匹配。建议加载辅码表时生成两套结构：展示字符串继续用于 comment，匹配索引用于热路径。

结构 用途 建议值
aux_display[char] 候选注释展示。 "pe,xx"，保持现状。
char_aux_index[char] 单字快速匹配。 { first = {p=true}, second = {e=true}, pair = {pe=true} }
word_aux_cache[word] 多字词按需聚合。 { firstSet, secondSet, pairSet, firstSeq, secondSeq }
syllable_aux_cache[key] 断句/探路音节集合。 区分 exact:ji、pred:j、miss:...，使用 LRU。 
-- 建议形态：加载辅码时一次构建
char_aux_index["踩"] = {
  first = { p = true },
  second = { e = true },
  pair = { pe = true },
  display = "pe"
}

local function match_aux_index(index, aux)
  if not index or aux == "" then return aux == "" end
  if #aux == 1 then
    return index.first[aux] or (AuxFilter.matchmode == 0 and index.second[aux])
  end
  return index.pair[aux] or (AuxFilter.matchmode == 0 and index.pair[aux:reverse()])
end

如果目标 Rime Lua 环境确认支持稳定 bit 操作，可以把 first/second 从表进一步压成 26 位 bitmask。否则表结构更稳，且已经能消除大量字符串扫描。

2. 把 fullAuxCache 从字符串串联改为聚合索引

现在多字词首次命中时会调用 AuxFilter.fullAux()，按字符拼接首码串和次码串。建议多字词缓存直接聚合单字索引，避免每次 AuxFilter.match() 再扫描字符串。

word_aux_cache[word] = {
  first = { h = true, j = true },
  second = { h = true, b = true },
  pair = { hh = true, jb = true },
  len = 2
}

3. 为预测匹配加有界 LRU，而不是完全不缓存

现有代码不缓存预测匹配，原因是避免不同上下文结果不稳定和内存膨胀。这个判断合理，但可以更细：预测结果按 pred:<syllable> 缓存到固定容量，例如 128 或 256 项。这样短时间连续探路不会反复扫字典，内存也可控。

local syllable_aux_lru = {
  max = 256,
  map = {},
  order = {}
}

-- key 示例：
-- exact:ji
-- pred:j
-- miss_exact:xyz

4. 缓存 preedit 元数据而不是缓存可变数组

split_pinyin() 缓存返回数组，历史上已经出现过“调用方修改数组污染缓存”的问题。建议缓存不可变元数据，调用方需要变更时显式复制。

preedit_meta_cache["han xin"] = {
  parts = {"han", "xin"},
  byte_prefix = {3, 6},
  count = 2
}

高频热路径和低频尖刺改造建议

步骤 1将普通辅码匹配从字符串扫描迁移到索引表。

这是普通单码/双码筛选每次按键都会走的路径，优先级应高于断句和分心。先保留现有 AuxFilter.fullAux_precomputed 和 fullAuxCache，新增 char_aux_index / word_aux_cache 并让 main_main() 优先使用新索引。稳定后再删除旧结构，避免长期双份内存。

步骤 2把候选处理改为单遍历。

候选迭代也是普通筛选高频路径。当前第一遍找到首候选并调用 main_main()，第二遍再次处理全部候选。可以改为一遍处理，首次符合条件时记录 firstcandi/rawpreedit。

local firstcandi, rawpreedit
for cand in input:iter() do
  if not need_filter or #split_pinyin(cand.preedit) == 1 then
    if not firstcandi then
      firstcandi, rawpreedit = cand, cand.preedit
    end
    main_main(env, cand)
  end
end

需要回归单字模式、双码辅码、首候选去重状态；分心路径只作为兼容回归项，不应主导设计。

步骤 3把 get_syllable_aux_set() 的缓存策略改为小容量有界缓存。

这一步服务于断句、修音、分心等低频能力。精确匹配可以继续永久缓存；预测匹配和失败结果建议使用小容量 LRU 或帧内缓存，目标是避免偶发功能触发时卡顿，而不是提升日常输入主路径吞吐。

缓存层 生命周期 适用内容
永久进程缓存 进程级 精确音节成功结果、明确无结果的精确音节。
LRU 缓存 进程级有容量 预测匹配结果，例如短音节、简拼探路；建议容量从 64 或 128 起步。
轮次缓存 每次 func() 重置 同一候选列表中重复出现的 preedit 音节。
步骤 4减少 candisub:new() 的 table 分配。

slice()、transform_preedit()、split_pinyin() 组合会产生短生命周期数组。普通短词收益有限，长句、修音、断句更明显；可以在完成主路径优化后，再缓存 preedit + len 的转换结果，或者只在候选最终要 yield 时再构造 preedit。

具体代码级建议

短期可做

  • 加载辅码表时构建 char_aux_index，让普通筛选热路径使用布尔集合或 bitmask 匹配。
  • 将 fullAuxCache 改为词级聚合索引，匹配不再扫描字符串。
  • 把 main1.process_candidates() 的双遍历改成单遍历。
  • 把 fullAux() 里的字符串拼接改为 table 收集后 table.concat()。

中期重构

  • 在 get_syllable_aux_set() 内增加小容量 LRU 和本轮查询缓存，服务低频断句/修音/分心路径。
  • 让 parseIntelligentCode() 返回更多派生字段，减少下游重复解析 funccode。
  • 把 table.insert() 热路径替换为 t[#t + 1] = v。
  • 把 split_pinyin() 的返回对象视为只读，修音分支统一复制后修改。

暂不建议

  • 不建议先做大面积局部变量缓存和微型字符串优化。它们容易制造噪音，收益通常低于结构性改动。
  • 不建议无上限缓存预测匹配结果。短音节会制造大量上下文相关结果。
  • 不建议把 debug 版作为性能基准。debug 版日志和 JSON 序列化会显著改变耗时。

风险清单

风险 说明 控制方式
状态机顺序变化 候选单遍历会改变 S.counter、S.one_aux_firstcode 被设置的时机。 先覆盖普通单码/双码、单字/词组；主动/被动分心作为低频兼容回归样例。
预测缓存错误复用 预测匹配结果可能与上下文有关。 缓存 key 区分 exact/predictive；预测缓存有容量；必要时加 schema/version salt。
索引结构和展示结构不一致 辅码字符串和新索引同时存在时可能构建不一致。 单一加载函数同时产出两者；debug 模式抽样校验。
缓存数组被修改 split_pinyin() 已有历史污染问题。 缓存对象只读约定；修改前复制；命名上区分 meta.parts 和 fresh_parts。

建议验收标准

  • 普通辅码筛选每轮候选遍历次数从“两遍”降为“一遍”。
  • 低频长句断句场景中 iter_dict() 调用次数可解释，重复音节命中小容量缓存。
  • 辅码匹配函数不再对候选的首码/次码字符串做线性扫描。
  • debug/release 业务分支保持一致，debug 只增加观测逻辑。
  • 未配置 speller/initials 的吞键路径仍能正确 commit，不出现尾段候选污染。

本报告是静态分析报告，建议下一步先做阶段 A 的计数器，再根据实际数据决定是否进入数据结构重构。
